# asis — development, as is

開発を、あるがままに見える化する道具の設計。コマンドは `asis`。

## 1. コンセプト

**起票を強いる道具は、使われなくなる。**

進捗管理が続かないのは、人が怠けるからではない。作業のほかに「書く」「動かす」を求めるからだ。AI が実装する開発では、仕事は入力より速く進む。入力を待つ道具は、すぐに実態とずれ、信用されなくなり、捨てられる。

だからこのアプリは、何も強いない。

- **入力させない。** 状態は誰も動かさない。GitHub で起きた事実だけで動く。
- **書かなくても壊れない。** issue が無い PR も、そのまま見える。
- **書くことが得になるようにする。** issue は報告ではなく、AI への指示になる。書けばそのまま仕事が始まる。
- **人には、確かめるべきものだけが順番に届く。**

AI 駆動開発を、計画で縛らず、起きているままに見える化する。管理する道具ではなく、観測する道具である。

機能を足すかどうかは「入力を強いていないか」で判定する。

## 2. 言葉

| 言葉 | 意味 |
|---|---|
| プロジェクト | GitHub の repo を 1 つ以上まとめたもの。repo の中の定義ファイル 1 枚で決める |
| タスク | GitHub の issue 1 件。目的とできたと言える条件を持つ。AI への指示を兼ねる |
| PR | GitHub の pull request。タスクに 0 本以上 つながる |
| 番 | その PR・タスクを次に進められる人 |
| 手元の作業 | この PC の worktree・ブランチ・ターミナルのペインで動いている、まだ PR になっていない作業 |

タスクと PR は多対多。タスクに PR が何本付いてもよく、1 本の PR が複数のタスクにつながってもよい。タスクにつながらない PR もある。

## 3. 正本と置き場

**アプリはデータを預からない。** サーバーも DB も持たない。使う人の PC の上で動き、その人の権限で GitHub を読む。repo の中身は、その PC と GitHub の間だけを流れる。

| もの | 正本 |
|---|---|
| タスクの題・本文・担当・開閉 | GitHub の issue |
| PR・レビュー・テスト・取り込み・デプロイ | GitHub |
| メンバー | GitHub の repo の権限。repo を見られる人が、同じものを見られる |
| プロジェクトの定義(まとめる repo・役割・数えないチェック) | repo の中の定義ファイル(`.asis.toml`) |
| 自分がどの repo を見るか、その repo で誰の分を出すか | その人の PC の設定ファイル |
| PR の状態・番・タスクの状態 | 保存しない。毎回 計算する。同じ事実から計算するので、誰の PC でも同じ結果になる |
| 手元の作業 | その PC の git と、ターミナルの状態 |

PC に置くのは一時的な写しだけ。消しても GitHub から作り直せる。

共有するものは GitHub に置く。アプリの中だけの招待・権限・役割の管理は持たない。

| やりたいこと | やり方 |
|---|---|
| プロジェクトを登録する | repo に定義ファイルを 1 枚 入れる |
| 自分の画面に出す | 見る repo に足す(`asis add owner/repo`) |
| メンバーを招待する | GitHub でその repo の権限を渡す。相手は、見る repo に足す |
| 決まりを変える | 定義ファイルを直す。その repo を見られる全員に反映される。変更には GitHub の履歴とレビューが付く |
| メンバーを外す | GitHub で repo の権限を外す |

定義ファイルを置かない repo は、その repo 1 つを既定の決まりで見る。repo にファイルを置けないときは、同じ内容を手元の設定ファイルに書ける(その場合は共有されない)。

## 4. つなぎ方の規則

PR をタスクにつなぐ手がかりは、上から順に見る。推測はしない。

1. GitHub が持つ PR と issue のリンク(PR の本文の `Closes #12` など)
2. PR の本文の `Refs #12`。別の repo の issue は `owner/repo#12`
3. ブランチ名が issue の番号で始まる(`12-short-name`)。種類を前に付ける決まりの repo に合わせて、最後の区切りの頭でも読む(`feature/12-short-name`)
4. 上のどれかでつながった PR の上に積んだ PR は、同じタスクにつながる

守る決まりは 2 つだけ。

- ブランチ名を issue の番号で始める。
- そのタスクを終わらせる PR には `Closes #12`、途中の PR には `Refs #12` を書く。

この 2 つは人ではなく AI が守る(§8)。

## 5. PR の状態と番

PR ごとに、次の表を上から順に当てて最初に当たった行で決める。

| 事実 | 状態 | 番 |
|---|---|---|
| 本番に出た | 本番 | なし |
| 取り込み済みで、本番にまだ出ていない | 取り込み済み | 本番に出す人 |
| 閉じられた(取り込まれずに) | 取り下げ | なし |
| 下書き | 実装中 | 作者 |
| 取り込み先とぶつかっている | 直し待ち | 作者 |
| テストが落ちている | 直し待ち | 作者 |
| 直しを頼まれた、または最後の push のあとに人のコメントがある | 直し待ち | 作者 |
| テストが動いている | テスト中 | なし |
| 承認済み | 取り込み待ち | 取り込む人 |
| 上のどれでもない | 確認待ち | 確認する人 |

- 役割(確認する人・取り込む人・本番に出す人)は、定義ファイルに GitHub のアカウント名で書く。`author` と書くと、その PR を出した本人を指す。
- 確認する人 = GitHub でレビューを頼まれた人。居なければ、定義ファイルに書いた人。それも無ければ、作者以外のメンバー。自分の PR は自分では確認しないので作者は外す。外して誰も残らなければ作者(1 人のプロジェクト、または確認する人に書かれた本人の PR)。定義ファイルに確認する人が書いてあるときは、書かれていないメンバーへは回さない。
- 取り込む人・本番に出す人は、書かなければ作者。
- 役割は「誰の番か」を出すためのもので、何かを禁止はしない。禁止は GitHub の設定(ブランチの保護)でやる。
- bot のコメントは数えない。
- チェックは 1 つずつ見る。落ちているものが 1 つでもあれば「落ちている」、無くて動いているものがあれば「動いている」。プロジェクトの設定で、数えないチェックを名前で外せる(プレビューの配置のように、落ちていても取り込みを止めないもの)。
- 落ちているチェックの名前を、理由に出す。
- どの行で決まったかを、理由として 1 行で出す(例:テストが 2 つ落ちている)。
- 番が付いてからの時間を出す。3 日 動きが無いものには印を付ける。

本番に出たかは、GitHub のデプロイの記録で決める。取り込みの commit が、成功した最新の本番デプロイに含まれていれば「本番」。含まれているかは、時刻ではなく、既定のブランチの commit の順番で決める。デプロイの記録が無いプロジェクトは、設定で「取り込み = 本番」にできる。

## 6. タスクの状態

つながっている PR の束から決める。上から順に当てる。

| 束の事実 | 状態 |
|---|---|
| issue が閉じていて、終わっていない PR が無い | 完了 |
| PR が 1 本以上あり、全部が本番に出たが、issue が開いている | 本番に出た・閉じていない |
| どれかが直し待ち・実装中・テスト中 | 実装中 |
| どれかが確認待ち・取り込み待ち | 確認待ち |
| どれかが取り込み済み(本番待ち) | 本番待ち |
| PR が無く、番号で始まるブランチがある | 実装中 |
| PR もブランチも無い | やること |

- 取り下げた PR は、無かったものとして扱う。
- タスクの番 = 束の中で番が付いている PR の番。複数あれば全員。
- issue が閉じているのに開いた PR が残っているときは、ずれとして出す。
- 人も AI も、状態を直接 変えられない。

## 7. 画面

出すものは 1 つ。最初に開くのは、プロジェクトの今。個人のやることの一覧を別の画面にしない(見せるのは開発の今であって、個人の受信箱ではない)。

- 今 動いているものを全部 出す。タスクを状態ごとに並べる。
- タスクにつながっていない PR は、別の段にまとめて出す。issue が 1 件も無くても、この段に全部の PR が並ぶ。
- つながる先を書いていても、その issue を読めていない PR(古く閉じた issue・別の repo の issue を指すもの)は、この段に出す。黙って消さない。
- 同じタスクの PR、積み上げた PR は 1 行にまとめる。
- 手元の作業を出す。どの worktree・どのペインが、どのタスクを触っているか。PR になる前から見える。
  - worktree は、ブランチで行に付ける。開いている PR のブランチと同じなら、その PR(とそのタスク)に付く。番号で始まるブランチなら、その番号のタスクに付く。
  - 印は 3 つ。AI が動いている / ペインが開いている / worktree だけある。
  - 手元に番号で始まるブランチがあれば、push する前でもタスクは「実装中」になる(その PC の上でだけ)。
  - どの行にも付かない worktree は、ペインが開いているものだけ「手元の作業(PR はまだ)」に出す。古い worktree を並べないため。
  - 手元の clone は、ペインが開いている場所・今の場所・設定に書いた探すフォルダから見つける。
- 自分の番のものは、一覧の中で色を付ける。
- 絞り込み:すべて / 自分の番 / 相手の番。「自分の番」は待たせている時間の長い順。
- 複数のプロジェクトをまたいで見られる。
- 大きな repo では、出す人を絞れる(その人たちが出した PR と、その人たちのタスクだけ)。何を見たいかは人によって違うので、repo の定義ではなく手元の設定に持つ。絞っていることは、repo の名前の横に出す。
- タスクを開くと、理由・PR の一覧(repo の名前つき)・目的・できたと言える条件が出る。
- 一覧の移動・開く・閉じる・絞り込みは、キーボードだけでできる。

同じ内容を 2 つの形で出す。どちらも §10 の判断の部品の結果を描くだけで、判断を持たない。

| 形 | 置き場所 | 役割 |
|---|---|---|
| TUI | ターミナルの中。AI を動かしているペインの隣 | 開発しながら見る。ターミナルの道具との連携 |
| GUI | 窓。デスクトップのアイコンから開く | 全体を広く見る。見た目を作り込む |

## 8. AI の入口

タスクは GitHub の issue なので、AI は GitHub の標準の道具で読み書きできる。アプリ専用の接続は作らない。用意するのは、AI に渡す短い手順書 1 枚だけ。置き場は `skill/asis/SKILL.md`。

手順書の中身:

- 「#12 を始めて」と言われたら、issue を読み、目的とできたと言える条件を作業の指示として扱う。
- ブランチ名を `12-` で始める。
- PR の本文に、途中なら `Refs #12`、これで終わるなら `Closes #12` を書く。
- 作業の途中で見つけて今回は直さないものは、新しい issue にして、元の issue を本文で指す。
- 状態を報告する文を issue に書かない(状態はアプリが事実から出す)。

AI ができないこと:状態を変えること。

ターミナルの道具(ペインと worktree を外から操作できるもの)があれば、アプリからタスクを選んで始められる。その issue 用の worktree とペインを開き、AI に「#12 を始めて」を渡す。道具が無くても、アプリ単体で動く。

## 9. 作る順

1. **判断の部品**: GitHub を読み、§4〜§6 の規則で状態・番・理由を出す。画面なしで、コマンドで結果が出る。
2. **TUI**: §7 の画面をターミナルに出す。手元の作業の表示と、ターミナルの道具との連携。
3. **GUI**: §7 の画面を窓に出す。アイコンとインストーラー。

最初の版に入れないもの(使ってみて無いと困ると分かったら足す):

- アプリの中での承認・取り込み
- 差分の表示(GitHub を開く)
- 人が付かずに動くクラウドの AI への割り当て
- AI が見つけた指摘の専用の置き場
- 通知・まとめの配信・数字の集計
- ターミナルを使わない人に見せるための出口

## 10. 作り

- **言語**: Rust。単体の実行ファイルで配る。軽さを条件にする(常駐時のメモリを測り、数字で管理する)。
- **判断は 1 か所**: §5・§6 の規則は、GitHub と手元の事実を入力に、状態と番と理由を返す 1 つの部品にまとめる。TUI も GUI もこの部品の結果を読むだけ。表の全部の行と、行の順番の入れ替わりをテストで押さえる。
- **GitHub の読み方**: 使う人の権限で読む。GitHub の公式コマンドでログイン済みなら、その権限を借りる。変化は定期的に取りに行く。キーを押したときは、すぐ全部 取り直す。
- **聞く量を抑える**: GitHub に聞ける量には 1 時間あたりの上限があり、同じアカウントで動くほかの道具と分け合う。毎回 全部は読まない。変わったかどうかの印(押し込み・PR・issue・本番デプロイの最後の時刻)を、全部の repo について 1 回の軽い問い合わせで聞き、印が変わった repo だけ読み直す。チェックが動いている PR がある repo は、終わりが印に出ないので次も読み直す。取りこぼしに備えて、10 分に 1 回は全部 読み直す。
- **黙って欠けさせない**: 件数の上限などで読み切れなかったときは、そのことを画面に出す。
- **GUI の描き方**: ブラウザの部品を埋め込まず、Rust で直接 描く。どの部品集を使うかは、同じ 1 画面を候補ごとに作り、メモリ・見た目・日本語入力を測って決める。
- **動かす場所**: 開発環境と同じ側で動かす(手元の作業を読むため)。Windows と Linux で動く。
- **公開**: 公開の repo に置き、誰でも入れられる。
